# 청구·결제 도메인 규칙

## 문서 목적

이 문서는 수동 구독 재활성화를 위해 도입한 청구와 결제의 현재 확정 규칙, 결정 이유와
후속 논의 대상을 기록한다. 구독의 생명주기와 선결제 이용 기간 규칙은
`docs/domain/subscription.md`를 함께 따른다.

---

## 구현 상태와 적용 범위

feature/11에서 Product·Subscription에 이어 Billing·Payment도 PostgreSQL로 전환했다.
기본 실행에서는 청구 준비·결제 시작·결과 반영이 같은 상품의 행 잠금과 짧은 트랜잭션에
참여한다. 잠금 안에서 최신 애그리거트를 다시 읽어 갱신 유실과 중복 결과 반영을 막는다.
외부 Gateway 호출 전에 PROCESSING 시도를 커밋하며 외부 호출은 트랜잭션 밖에서 수행한다.
Payment 성공·Billing 완료·Subscription 활성화는 함께 커밋하거나 함께 롤백한다.

V2 마이그레이션은 청구·결제 이력, 구독별 PENDING 청구와 청구별 PROCESSING·SUCCESS
결제의 유일성을 보장한다. 신규 저장과 기존 갱신을 구분하며 복원 시 상태 불변식을 확인한다.
만료된 청구에 결제를 요청하면 EXPIRED를 커밋한 뒤 409를 반환한다.
재시작 후에도 미완료 시도 ID와 시도 시각을 읽을 수 있고, PG 결과를 얻으면 승인 업무 날짜로
복구한다. 현재 Fake Gateway의 결과 저장소는 메모리이므로 **외부 결과 자체의 재시작 복구는
보장하지 않는다**. `in-memory` 프로필은 기존 단일 프로세스 테스트용이다.

V3는 결제창 인증 상관관계와 승인·보상 복구 기록을 저장한다. `toss-test` 프로필은
토스 테스트 승인·조회·전액 보상 취소를 연결하며 기본 구성의 Fake Gateway와 분리한다.
보상 완료 시 Billing을 CANCELLED로 종료하고 새 청구에서 현재 가격으로 재결제하는
정책을 확정했다. 아래 보상 취소 규칙과 [실행 안내](../toss-test.md)를 따른다.

`TossTestPaymentClient`는 테스트 시크릿 키만 허용하며 API 호스트를 고정한다.
연결 3초·응답 30초 제한은 결제 실패 판정 기준이 아니다. HTTP 오류·응답 유실을 FAILED로
변환하지 않는다. 승인 응답과 조회 결과의 식별자·금액·통화·타입을 검증한다.
자동 테스트는 PostgreSQL과 모의 토스 응답을 사용하며, 외부 테스트 상점의 카드 인증을
실행한 것으로 간주하지 않는다. 라이브 환경 구현과 실제 금액 거래는 제외한다.

2026-09-29 결정은 결제 거절 후 복구, 공급 불가 상품의 청구·결제 시작 차단과 청구 만료를
대상으로 한다.
외부 결제 요청 이후의 공급 상태 변경 대응과 환불·취소 정책은 별도 논의 대상으로 유지한다.

일반 환불·취소는 미결제 청구의 취소, 승인된 결제의
전액·부분 환불, 구독 종료와 잔여 이용권 처리의 책임을 구분해 후속 논의한다. 구체적인
조건과 금액 계산, 상태값 및 별도 모델은 아직 정하지 않는다. DB 실패 보상 취소에 대해
별도로 합의한 방향은 아래 “PostgreSQL 도입 시 구현할 보상 취소 규칙”에 기록한다. 향후 환불·취소를 도입해도
기존 결제 성공 사실은 보존하며, 환불을 표현하기 위해 SUCCESS를 FAILED로 바꾸지 않는다.

## 확정된 규칙: 재시도와 결과 확인

### 결제 시도의 생명주기

Payment는 결제 결과만이 아니라 특정 Billing에 대한 하나의 결제 시도를 표현한다.
Gateway 호출 전에 `PROCESSING` Payment를 생성하고 저장한다. `PROCESSING`은 외부
처리가 진행 중이거나 최종 결과를 아직 확인하지 못한 상태를 포함한다.

```text
PROCESSING -> SUCCESS: 승인 확인
PROCESSING -> FAILED: 명확한 결제 거절 확인
PROCESSING -> PROCESSING: Timeout 등으로 결과 미확정
PROCESSING -> CANCEL_PENDING: 승인 증거 보존 및 내부 미반영 확인 후 취소 결정
CANCEL_PENDING -> CANCELLED: PG 전액 취소 확인과 로컬 결과 반영 완료
```

현재 결정에서는 별도 `UNKNOWN` 상태를 추가하지 않는다. 동일 시도의 최종 결과가
확정되면 그 결과를 이력으로 보존하며, 재시도를 위해 기존 FAILED Payment를 다시
PROCESSING으로 바꾸지 않는다. 청구와 결제는 계속 별도 애그리거트로 유지하고
Payment가 BillingId로 청구를 참조한다.

### 새 결제 시도의 허용 조건

새 시도는 인증된 고객 소유의 Billing이 `PENDING`이고 아직 결제 시작 기한 전이며,
Subscription이 재활성화 대상이고 상품이 현재 AVAILABLE일 때 허용한다. 해당 Billing에
진행 중이거나 결과가 미확정인 Payment도 없어야 한다. 기존 FAILED Payment는 보존하고
새 Payment를 생성하므로 Billing과 Payment의 관계는 1:N이다.
매 시도는 Billing에 확정된 금액을 사용하고 상품 가격을 다시 확정하지 않는다.
PROCESSING Payment 생성과 Gateway 호출 전에 Subscription.validatePaidReactivation을
호출해 기간 문맥(currentPeriod, pausedAt, scheduledResumeDate, nextBillingDate)과
시도 시작 KST 날짜가 일시정지 날짜보다 빠르지 않은지 검사한다. 검증은 상태를 바꾸지
않으며, 실패하면 Payment를 생성하거나 Gateway를 호출하지 않는다. 실제 승인 반영은
승인 날짜로 같은 검증을 다시 수행한다. 사전 검증이 이후 구독 변경까지 보장하지는 않는다.

승인되면 해당 Payment를 SUCCESS로 확정하고 Billing을 PAID로 변경하며 구독을
재활성화한다. PAID Billing에는 새 결제를 허용하지 않는다. 명확히 거절되면 해당
Payment를 FAILED로 확정한다. 구독이 여전히 재활성화 대상이면 구독 도메인 행위가
PAUSED를 유지하며 PAYMENT_FAILED를 추가한다. 이미 취소되는 등 대상이 아니면 구독은
변경하지 않으며, 이 때문에 PG 거절 사실의 기록을 막지 않는다.
Billing은 기한 전이면 PENDING을 유지해 같은 청구로 재시도할 수 있고, 기한이 지났으면
EXPIRED로 전이한다. 만료된 청구의 재시도는 새 Billing을 준비한 뒤 수행한다.

### 트랜잭션과 동시 실행 제어

동일 Billing의 결제 시작은 다음 단위로 처리한다.

1. 짧은 DB 트랜잭션 안에서 Billing의 상태·결제 시작 기한, 구독과 상품 공급 상태를
   확인하고, 진행 중 Payment가 없는지 확인한 뒤 PROCESSING Payment를 생성·저장하고
   커밋한다.
2. DB 트랜잭션 밖에서 외부 Gateway를 호출한다.
3. 결과가 확정되면 별도의 짧은 DB 트랜잭션에서 Payment, Billing과 Subscription에
   결과를 함께 반영한다.

진행 중 여부 확인과 시도 생성에는 잠금이나 제약조건 등 동시 실행 제어가 필요하다.
트랜잭션 어노테이션만으로 두 요청이 모두 검사에 통과하는 상황을 방지할 수 있다고
가정하지 않는다. DB 잠금·제약조건과 트랜잭션 어댑터는 `docs/adr/persistence.md`를 따른다.
로컬 트랜잭션의 롤백은 외부 PG에서 이미 승인한 결제를 취소하지 않는다.

### Timeout과 결과 확인

응답 대기 시간이 끝났다는 사실은 결제 실패 또는 취소의 근거가 아니다. Timeout이면
기존 Payment를 PROCESSING으로 유지하고 같은 Billing의 새 시도를 차단한다. 고객에게는
실패 확정이 아닌 결과 확인 중임을 안내한다. 논의 중 예시로 든 10초는 실제 설정값으로
확정하지 않는다.

PG가 제공하는 웹훅과 결제 조회를 이용해 동일 시도의 최종 결과를 확인한다. 미확정 건은
백그라운드에서 확인하고, 장기간 해소되지 않는 건은 운영자가 PG 기록과 대조하도록
넘긴다. 오래 지났다는 이유만으로 FAILED 처리하거나 새 결제를 허용하지 않는다.
현재 Fake 연동의 백그라운드 확인 간격은 기본 30초이며
`payment.reconciliation.delay-ms`로 설정한다. `payment.reconciliation.enabled=false`로
중지할 수 있다. 조회는 기존 시도의 결과만 확인하며 결제를 다시 요청하지 않는다.
실제 PG의 조회 제한에 맞춘 주기·횟수·운영 전환 기준과 웹훅은 후속 연동에서 정한다.

동기 응답, 웹훅과 조회 결과는 같은 Payment에 연결해야 한다. 같은 결과가 중복되거나
순서가 바뀌어 도착해도 Payment 결과와 구독 이용 기간을 중복 반영하지 않는다. PG 승인
뒤 로컬 저장 실패나 서버 중단으로 결과가 반영되지 않은 시도도 결과 확인 대상이다.

### 같은 요청의 재전송과 새로운 시도

명확한 거절 후 고객이 다시 결제하는 것은 새 Payment를 만드는 새 시도다. 반면 결과를
모르는 기존 요청을 다시 보내는 것은 같은 시도의 재전송이다. PG가 멱등키를 지원하는
경우 동일 시도의 재전송에는 같은 키와 같은 요청 내용을 사용하고, 새 시도에는 별도
키를 사용한다. 키는 최초 외부 요청 전에 해당 시도와 연결해 보존해야 한다.

PG별 멱등키 유효기간과 지원 API를 확인해야 하며, 키가 만료됐다는 사실만으로 새 시도를
허용하지 않는다. 결과 조회에 사용할 외부 식별자, 웹훅 검증과 조회 계약은 실제 PG 선정
후 정한다. 결과가 미확정인 동안 새 시도를 막는 원칙은 PG의 멱등키 지원 여부와 무관하다.

### 결과 시각과 현재 결과 반영의 한계

Gateway 결과의 `completedAt`은 KST로 정규화한 승인·거절 시각이다. 지연 조회에도
같은 값을 반환하며, 성공 시 구독의 이용 구간은 이 승인 날짜를 기준으로 연다.
`Payment.attemptedAt`은 최초 시도 시작 시각으로 유지한다. 결과 확인 날짜로 승인
날짜를 바꾸지 않는다.

결과 반영 전에 구독이 취소되는 등 재활성화 조건이 달라진 경우 구독 도메인이 승인을
거절한다. 토스 연동에서는 승인 증거의 REVIEW 단계와 Payment PROCESSING을 보존한다.
후속 자동 처리는 중단하고 운영 확인 대상으로 남긴다.
승인 사실을 FAILED로 바꾸거나 자동으로 이용권을 부여하지 않는다. 외부 승인과 구독
변경의 충돌에 대한 보상·운영 조정 정책은 후속 논의한다. 토스 연동은 승인
증거를 별도로 영속 보존하여 도메인 충돌과 DB 실패를 구분한다.

## 확정된 규칙: 청구 만료와 재청구

### 결제 시작 기한

Billing 생성 시 `expiresAt = createdAt.plusMinutes(10)`으로 확정한다. 애플리케이션에서
주입한 KST Clock의 시각을 기준으로 판단하며 도메인이 현재 시각을 직접 조회하지 않는다.
`now < expiresAt`일 때만 새 결제를 시작할 수 있고, 정확히 expiresAt부터 새 시도를
허용하지 않는다. Payment 시작 시점은 PROCESSING 시도를 생성·저장하는 실행 경계다.

기한 도달과 EXPIRED 상태 전이는 구분한다. 기한 내 시작한 PROCESSING Payment가 있으면
결과 확인을 위해 Billing을 PENDING으로 유지하되, 기한이 지난 뒤 새 시도는 차단한다.
조회나 재요청으로 expiresAt을 연장하지 않는다.

### 기한 도달과 진행 중 결제의 처리

| Billing 상태와 조건 | 처리 |
|---|---|
| PENDING, 기한 전, 진행 중 Payment 없음 | 기존 Billing 재사용 및 새 결제 시도 허용 |
| PENDING, 기한 도달, PROCESSING Payment 없음 | EXPIRED로 전이, 기존 청구로 결제 차단 |
| PENDING, 기한 도달, PROCESSING Payment 있음 | PENDING 유지, 새 시도·대체 청구 생성 차단, 결과 확인 |
| 기한 내 시작한 Payment의 승인 확인 | 기한 경과 여부와 무관하게 Payment SUCCESS, Billing PAID 처리 |
| Payment 거절 확인 시 아직 기한 전 | Payment FAILED, Billing PENDING 유지 |
| Payment 거절 확인 시 기한 도달 | Payment FAILED, Billing EXPIRED 처리 |
| Payment Timeout 등 결과 미확정 | PROCESSING 유지, 기한 경과만으로 실패·만료 처리하지 않음 |

만료는 새 결제 시작 자격을 종료하는 행위다. 기존 승인 사실이나 실패 이력을 삭제하지
않고 구독 상태와 이용권도 만료만으로 변경하지 않는다. 늦게 확인한 승인에 대한 구독
결과 반영은 기존 승인 처리 원칙을 따르되, 처리 도중 구독·공급 상태가 변경된 경우의
조정 정책은 별도 논의 대상으로 유지한다.

Billing 상태 전이는 `PENDING -> PAID`, `PENDING -> EXPIRED`, 보상 완료 시
`PENDING -> CANCELLED`다. EXPIRED와 CANCELLED를
다시 PENDING으로 되돌리지 않는다. PAID는 현재 설계 범위에서 나가는 전이가 없으며,
향후 환불·취소의 표현 방식은 미정이다.

### 만료 뒤 새 청구 준비

기존 청구가 만료된 뒤 준비 요청이 오면 소유권, 구독 재활성화 조건과 현재 상품 공급
상태를 다시 확인한다. 조건을 만족하면 현재 상품 가격으로 새 Billing을 만들고 새로운
10분의 기한을 부여한다. 기존 Billing과 연결된 Payment 이력은 그대로 보존한다.
결제 요청이 만료된 Billing의 금액을 바꾸거나 자동으로 다른 Billing을 결제하지 않는다.
고객은 새 청구의 금액을 확인한 뒤 새 Billing으로 결제한다.

기한이 지난 기존 Billing에 PROCESSING Payment가 있으면 새 Billing을 발급해 우회하지
않고 기존 시도의 결과를 확인한다. 성공하면 기존 Billing을 PAID로 완료하고, 거절이면
만료시킨 뒤 다음 준비 요청에서 새 Billing을 발급한다.

결제 시작, 결과 확정과 만료 판단은 동일 Billing에 대해 원자적으로 조율해야 한다.
동시 준비 요청으로 같은 구독에 대체 청구가 여러 개 만들어지는 것도 방지해야 한다.
현재 구현은 청구 준비·결제 시작과 거절 결과 반영 시 만료를 판단한다. 별도 만료
배치는 없으며 Checkout GET은 상태를 변경하지 않는다. 저장 상태가 PENDING이어도
expiresAt에 도달하면 결제 시작이 차단된다. 준비·Checkout 응답 모두 expiresAt을 제공한다.

## 확정된 규칙: 공급 상태에 따른 청구·결제 차단

`SupplyStatus.AVAILABLE`인 상품만 재활성화 청구 준비와 새 결제 시도를 허용한다.
`TEMPORARILY_UNAVAILABLE` 또는 `DISCONTINUED`이면 두 요청을 모두 거절한다.

- 청구 준비: 인증·소유권과 구독의 재활성화 조건을 확인한 뒤 현재 Product 공급 상태를
  확인한다. 새 Billing을 만들 때뿐 아니라 기존 PENDING Billing을 반환할 때도 검사한다.
- 결제 실행: 청구 준비 때의 검사 결과를 신뢰하지 않고, 새 PROCESSING Payment를 생성해
  Gateway를 호출하기 전에 현재 Product 공급 상태를 다시 확인한다. 재시도에도 적용한다.
- 공급 불가로 거절하면 새 Billing이나 Payment를 만들거나 Gateway를 호출하지 않는다.
  기존 청구와 결제 이력은 보존한다. PG의 승인 거절이 아니므로 FAILED Payment나
  PAYMENT_FAILED를 추가하지 않는다.
- 공급 상태 확인은 가격 재산정과 구분한다. 기존 Billing의 확정 금액은 유지한다.

Product가 공급 가능 여부를 판단하고, 청구 준비와 결제 유즈케이스가 Product를 로드해
그 판단을 사용한다. Payment 애그리거트에 Product 객체나 저장소 의존성을 넣지 않는다.

이 규칙은 청구 준비 후 공급이 중지된 상품에 새로운 결제를 시작하는 것을 차단한다.
검사 직후 또는 외부 결제 진행 중 공급 상태가 바뀌는 경쟁 조건까지 재조회만으로
해결된다고 가정하지 않는다. 그 상황의 승인 결과 반영, 보상 및 환불 정책은 아직
미정이며, 공급 불가라는 이유로 이미 발생한 PG 승인 사실을 FAILED로 바꾸지 않는다.
결과가 미확정인 기존 Payment의 조회·웹훅 처리는 새 결제 시도와 구분한다.

## 현재 구현

### 청구와 결제의 책임

`Billing`은 고객·구독·상품 식별자, 가격 스냅샷, 청구일, 생성 시각과 만료 시각을 가진다.
상태는 PENDING, PAID, EXPIRED, CANCELLED이며 각 전이는 Billing의 도메인 행위가 소유한다.
청구 안에 결제 컬렉션을 두지 않는다.

`Payment`는 BillingId, 청구와 동일한 금액, 시도 시각과 상태를 가진다. PROCESSING을
SUCCESS 또는 FAILED로 확정한다. DB 미반영이 확인된 승인 건은 CANCEL_PENDING을 거쳐
CANCELLED로 확정하며 승인 거래 식별자와 별도 취소 증거를 보존한다. 확정된 결과는
재시도를 위해 변경하지 않는다. PAID와 SUCCESS는 현재 범위에서 최종 상태이며
환불·거래 취소로 나가는 전이와 별도 사실 모델은 후속 논의 대상이다.

### 가격과 재활성화 일정

처음 준비하거나 만료 후 새로 발급하는 Billing에 현재 Product.basePrice를 스냅샷한다.
Checkout 표시 금액과 Gateway 요청 금액은 Billing.amount이며 고객이 금액을 전달하지
않는다. 기존 청구의 공급 상태를 다시 검사해도 청구 금액과 유효기간은 변경하지 않는다.

승인 시 PAUSED이고 remainingPaidDays가 0인 구독을 재활성화한다. 승인 KST 날짜를
paymentDate로 사용해 다음 상태를 반영한다.

```text
Billing.status = PAID
Payment.status = SUCCESS
Subscription.lifecycleStatus = ACTIVE
billingAnchorDay = paymentDate.dayOfMonth
nextBillingDate = 새 anchor 기준으로 paymentDate 뒤에 처음 도래하는 결제일
currentPeriod = paymentDate ~ nextBillingDate.minusDays(1)
remainingPaidDays, pausedAt, scheduledResumeDate = null
suspensionReasons에서 PAYMENT_FAILED만 제거
```

기존 월말 보정 규칙을 재사용한다. 2026-01-31 승인이라면 anchor는 31, 다음 결제일은
2026-02-28, 새 이용 구간은 2026-01-31부터 2026-02-27까지다. 2028년 1월 31일이면
다음 결제일은 2월 29일이다. PRODUCT_UNAVAILABLE 등 다른 실행 차단 사유는 유지한다.

거절 시 `recordReactivationPaymentDeclined()`가 재활성화 대상 구독에만 PAYMENT_FAILED를
추가한다. 이 행위는 구독의 생명주기·기간 문맥·일정을 변경하지 않는다.
Timeout은 이 사유를 추가하지 않는다. 실패 후 재시도에서도 이력과 금액은 보존한다.

### 실행 경계와 Gateway 계약

`BillingExecutionPort`는 같은 SubscriptionId에 대한 청구 준비·결제 시작·결과 반영의
상호 배제를 제공한다. `in-memory` 프로필의 어댑터는 고정 개수의 잠금을 사용한다. 같은
구독에는 같은 잠금이 선택되며, 외부 Gateway 호출과 결과 조회는 잠금을 잡지 않는다.
외부 호출 전에 저장한 PROCESSING을 통해 동시 시도와 만료 뒤 대체 청구를 차단한다.

Payment 저장소는 ID 조회, Billing별 진행 중 시도 조회와 미완료 ID 목록을 제공한다.
동기 응답, 고객의 결과 확인과 백그라운드 조회는 동일한 결과 반영 로직을 사용한다.
이미 확정한 Payment에는 이용 기간을 중복 반영하지 않는다.

Gateway 요청에는 PaymentId, BillingId와 금액을 전달한다. Fake Gateway는 PaymentId를
멱등키로 삼아 같은 요청에 같은 결과를 반환하고, 같은 키로 다른 내용을 보내면 거절한다.
응답 미확정 시에는 키를 유지하며 Fake의 approvePending/declinePending으로 후속 결과를
설정할 수 있다. 이 제어 메서드는 테스트용이며 HTTP로 공개하지 않는다.

기본 PostgreSQL 구성은 `SubscriptionExecutionPort`와 상품 행 잠금을 공유해 공급 변경과
구독 변경을 조율한다. 청구 준비도 잠금 획득 후 구독을 다시 로드한다. 다만 PG 호출 중에는
잠금을 보유하지 않으므로 그 사이의 공급·구독 변경 정책을 새로 확정하는 것은 아니다.
Payment 성공·Billing 완료·Subscription 활성화는 한 트랜잭션으로 반영하며 실패하면 함께
롤백한다. 미완료 시도와 토스 승인·보상 기록은 PostgreSQL에 남아 재시작 후 다시 읽는다.
다만 기본 Fake Gateway의 외부 결과는 메모리에만 있으므로 해당 결과의 재시작 복구는
보장하지 않는다. 토스 테스트 프로필의 복구는 아래 보상 취소 규칙을 따른다.

### 인증·인가와 HTTP API

Billing과 Payment API는 CUSTOMER 역할을 요구한다. 준비는 Subscription 소유권,
Checkout은 조회 모델의 Billing 고객, 결제 시작과 결과 확인은 Billing 소유권을 각각
검사한다. 결과 확인은 해당 Payment가 경로의 Billing에 속하는지도 검증한다.

```text
POST /subscriptions/{subscriptionId}/reactivation-billing
GET  /billings/{billingId}/checkout
POST /billings/{billingId}/payments
POST /billings/{billingId}/payments/{paymentId}/reconcile
```

결과 확인은 로컬 상태를 갱신할 수 있으므로 POST다. Gateway 조회로 기존 시도의
결과만 확인하고 새 결제를 시작하지 않는다. Checkout GET은 전용 조회 포트를 사용한다.

- 준비·Checkout: 200, 생성 시각에 확정된 expiresAt을 제공한다.
- 결제 시작·결과 확인: 확정 결과는 200과 SUCCESS/FAILED/CANCELLED,
  미확정이면 202와 PROCESSING/CANCEL_PENDING.
- 진행 중 결제가 있는 Billing의 새 시도: 409, ProblemDetail에 기존 paymentId 제공.
- 만료·결제 완료 청구, 부적격 구독 또는 공급 불가 상품: 409.
- 존재하지 않는 리소스 또는 Billing과 Payment의 연결 불일치: 404. Checkout·결제 시작·
  결제 결과 반영 중 청구가 참조하는 구독을 찾지 못한 경우도 SubscriptionNotFoundException으로
  404를 반환한다. 시작 전이면 Payment 생성·PG 호출을 하지 않으며, 이미 진행 중인 시도는
  구독 부재만으로 FAILED 처리하거나 재결제를 허용하지 않는다.
- 0 이하 식별자: 400. 타인 소유 리소스: 기존 보안 정책에 따라 403.

고객은 PROCESSING이면 결과 확인 API를 호출하며, EXPIRED로 거절된 경우 새 청구를
준비해 금액을 확인한 뒤 결제한다. 만료된 청구를 요청했다고 새 청구를 자동 결제하지 않는다.

## 결정 이유

### 청구 준비와 결제 시작에서 공급 상태를 각각 확인하는 이유

청구 준비와 결제 실행은 서로 다른 요청이며 그 사이에 공급이 중지되거나 영구 종료될
수 있다. 청구 준비 때 한 번 검사한 결과로 결제 시점의 공급 가능 여부를 보장할 수 없다.
기존 청구의 가격은 보존하되 현재 상품의 공급 가능 여부는 각 실행 경계에서 확인한다.

### 만료 시 진행 중 결제의 결과를 기다리는 이유

기한이 지난 뒤에도 기한 내 시작한 외부 결제가 승인될 수 있다. 시간 경과만으로 기존
청구를 만료하고 새 청구를 발급하면 같은 구독에 두 결제가 성공할 수 있다. 따라서
기한은 새 시도만 제한하고 기존 시도의 결과를 확인한 뒤 청구의 최종 상태를 결정한다.

### 결과 미확정과 명확한 거절을 구분하는 이유

응답이 끊긴 뒤에도 PG에서 승인이 완료될 수 있다. 이를 실패로 보고 새 시도를 허용하면
같은 청구에 중복 출금될 수 있다. 기존 시도의 결과 확인과 실패 후 새 결제를 구분한다.

### 외부 호출 전 시도를 저장하고 트랜잭션을 나누는 이유

외부 호출 전에 시도를 남겨야 동시 요청을 차단하고 서버가 중단돼도 미완료 시도를 찾을
수 있다. PG 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않고, 최종 결과 반영은 별도
트랜잭션으로 묶는다.

### Billing과 Payment를 분리한 이유

청구할 거래 가격이 확정됐다는 사실과 실제 돈을 받으려 시도한 결과는 생명주기와 변경
이유가 다르다. 결제 거절 뒤에도 청구는 유효하므로 하나의 상태 모델로 합치지 않는다.

### 기존 PENDING Billing을 반환하는 이유

Checkout 진입 뒤 준비 요청이 반복되더라도 유효기간 내에는 최초 확정 가격을 보존한다.
기한이 지난 청구는 진행 중 결제 유무에 따라 만료하거나 결과를 기다리고, 만료 후 새
청구는 현재 가격을 확정한다.

### 결제 성공일에 새 구독 회차를 여는 이유

새 이용권은 실제 결제가 승인된 뒤에만 제공한다. 요청일이나 Billing 생성일이 아니라
성공 업무 날짜를 시작일로 사용해야 결제 전 기간을 유료 이용 기간으로 잘못 제공하지
않는다.

## PostgreSQL 도입 시 구현할 보상 취소 규칙

이 절은 사용자와 합의한 청구·결제 영속화 및 보상 취소의 구현 요구사항이다. DB 선택은
2026-10-03 PostgreSQL로 변경했고 feature/11의 토스 테스트 연동에 구현했다. 고객 요청 환불·부분 환불과 구독 이용권 회수 정책은 계속 별도 논의 대상이다.

### 취소 대상과 내부 반영 확인

보상 취소 대상은 PG 승인 후 구독 활성화를 위한 DB 업데이트가 반영되지 않았음이
확인된 건이다. DB 오류가 발생했다는 이유만으로 미반영을 단정하지 않는다.

- 내부 반영 완료 확인: 정상 결제로 완료 처리하고 보상 취소하지 않는다.
- 롤백 등으로 미반영 확인: 보상 취소 절차를 시작한다.
- 커밋 도중 연결 단절 등 반영 여부 불확실: 재결제를 차단하고 DB 복구 후 확인한다.

구독 취소 등 도메인 검증 실패를 이 DB 실패 정책에 자동으로 포함하지 않는다. 해당
경우의 보상 정책은 아직 미정이며, 현재는 기존 시도를 확인 대상으로 유지한다.

### 함께 반영할 세 가지 구현 요구사항

1. **내부 결과의 원자적 반영**: Payment 성공 확정, Billing 완료와 Subscription 활성화를
   하나의 DB 트랜잭션으로 커밋하거나 함께 롤백한다. PG 호출은 이 트랜잭션 밖에서 수행한다.
2. **취소 결정의 선저장과 승인 반영 차단**: 미반영 여부 확인과 취소 결정 저장은 동시
   결과 처리와 경쟁하지 않도록 조율한다. 취소 결정과 멱등키를 영속 저장한 뒤 PG 취소를
   요청한다. 취소 결정 이후에는 동기 응답·조회·백그라운드 복구에 의한 구독 활성화를
   차단하며, 같은 청구나 대체 청구로 새 결제를 시작하는 우회도 차단한다.
3. **취소 결과 복구와 재결제 제한**: 취소 요청의 멱등키와 PG 조회로 결과를 복구한다.
   취소 응답이 유실되거나 PG 취소 후 로컬 저장이 실패하면 완료로 단정하지 않는다.
   PG 취소 완료 확인과 로컬 반영을 마친 뒤에만 구독·공급 상태 등 재결제 조건을 다시
   검사해 고객의 새 시도를 허용한다.

PG 호출 전 결제 시도를 영속 저장하고, 승인 식별자와 취소 요청·결과를 복구할 수 있게
보존한다. DB 장애로 취소 결정 자체를 저장하지 못한 경우도 기존 미완료 시도를 기준으로
복구해야 하며, 예외 처리에서 취소 API를 한 번 호출하는 것만으로 완료됐다고 보지 않는다.
승인 사실은 취소 후에도 보존하고 FAILED로 바꾸지 않는다. 취소 진행·완료를 표현할
상태는 Payment의 CANCEL_PENDING/CANCELLED와 별도 승인 기록으로 표현한다.
취소 완료 시 기존 Billing을 CANCELLED로 종료한다. 기존 청구에서 새 결제를 시작하지
않으며 고객이 새 청구를 준비할 때 현재 가격과 구독·공급 조건을 다시 검사한다.

### 승인 증거와 중단된 내부 반영 복구

PaymentApproval은 Payment에 종속된 승인·복구 사실이며 독립적인 구매나 청구가 아니다.
승인 거래 ID와 승인 KST 시각은 READY로 선저장한다. 구독 조건 검증 후 APPLYING과
시작 시각을 별도 커밋하고, 다음 짧은 트랜잭션에서 정상 결과 세 가지를 원자적으로 반영한다.
이때도 잠금 안에서 취소 결정 여부와 최신 구독을 다시 확인한다.

DB 예외 후 새 트랜잭션으로 SUCCESS가 확인되면 정상 완료이며 취소하지 않는다.
PROCESSING이고 도메인 조건이 유효하면 내부 미반영으로 확인하여 취소 결정을 커밋한다.
DB가 복구되지 않아 확인·취소 결정을 저장할 수 없으면 APPLYING 기록으로 복구한다.
동시 요청과의 경쟁을 피하기 위해 중단 여부 재확인은 시작 2분 뒤부터 수행하며,
시간만으로 취소하지 않고 같은 잠금 아래 SUCCESS 여부·도메인 조건을 다시 검사한다.
APPLYING 저장 직후 프로세스가 중단되어 결과 트랜잭션을 시작하지 못한 경우도 이 경로를 따른다.

취소 결정·멱등키·시각과 Payment CANCEL_PENDING을 함께 커밋한 뒤 외부 취소를 호출한다.
PG 결과를 조회하여 전액 취소 이력과 잔액 0을 확인하고, 취소 거래 ID·시각과 Payment·Billing
CANCELLED를 함께 반영한다. 이 사이의 장애는 같은 결정과 키로 복구한다.
도메인 검증 실패는 REVIEW로 남기고 자동 승인 반영·취소 모두 중단한다.

### 토스페이먼츠 연동 기준

- 승인된 결제의 전액 보상 취소를 대상으로 한다. 취소 API는
  `POST /v1/payments/{paymentKey}/cancel`이며 취소 사유를 전달한다.
- `paymentKey`는 결제 조회·취소에 사용하는 식별자다. 승인·취소 거래의
  `transactionKey`와 구분해 보존한다.
- 동일 취소의 재전송에는 같은 멱등키와 요청 내용을 사용한다. 토스 멱등키의 유효기간은
  최초 사용 후 15일이다. 기간 경과만으로 결과 미확정 건에 새 키를 발급하지 않고
  PG 조회와 운영 확인을 통해 이전 결과를 확인한다.
- 기존 30초 결과 확인 작업은 CANCEL_PENDING도 조회한다. 15일 이후에는 취소를
  재전송하지 않고 PG 조회와 운영 확인만 수행한다. REVIEW와 장기 미확정 건의 운영 처리
  API는 별도 범위다. Fake Gateway에는 취소 연동을 추가하지 않는다.

근거: [토스페이먼츠 결제·취소 API](https://docs.tosspayments.com/reference),
[멱등키 계약](https://docs.tosspayments.com/reference/using-api/authorization).

## 후속 논의 대상

다음 항목은 현재 구현 요구사항이 아니며 선제 구현하지 않는다.

- 최초 구독 결제와 결제 전 구매 의도 모델
- Order, Cart와 다상품 일괄 결제
- 자동 정기결제와 회차별 Scheduler·Batch
- 고객용 Payment 이력 조회 API
- 구독 취소 등 유효기간 경과 이외 사유에 의한 PENDING Billing 무효화
- PG별 멱등키 계약과 결과 조회·웹훅의 구체적인 연동 방식
- 별도 만료 배치의 필요 여부
- 자동결제와 Payment Method, 카드 저장
- 장기 미확정 건의 운영 처리 API와 알림
- Outbox·Event 도입 필요 여부
- 고객 요청 환불·결제 취소와 이용권 회수 정책(위 DB 실패 보상 취소와 별도)
- 공급 상태 확인 직후 또는 외부 결제 진행 중 공급 변경과 승인 결과의 처리 정책
