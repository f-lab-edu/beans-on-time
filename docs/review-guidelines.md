# 구현 후 리뷰 가이드

## 목적

이 문서는 코드 변경 후 자체 리뷰에서 사용하는 공통 판단 기준이다.

검토만 요청받은 작업에도 사용하되 지적과 수정 방향만 보고하고 파일을 수정하지 않는다.
기존 코드나 문서의 감사 요청에서는 diff 유무와 관계없이 사용자가 지정한 범위를
검토한다. 변경 후 리뷰에서는 현재 변경으로 인한 문제를 중심으로 판단한다.

리뷰는 실제 동작 오류, 도메인 규칙 위반, 아키텍처 경계 훼손과 회귀 위험을 찾는 데
집중한다. 코드를 더 많이 바꾸기 위한 절차로 사용하지 않는다.

구체적인 도메인 상태값, 불변식과 정책은 해당 애그리거트 문서가 소유한다. 이 문서는
그 내용을 복제하지 않고 리뷰할 관점을 제공한다.

---

# 리뷰 입력

리뷰 전에 다음 정보를 확인한다.

- 사용자가 요청한 동작과 변경 범위
- 현재 작업에서 변경한 전체 diff
- 변경한 코드의 인접 구현과 테스트
- `AGENTS.md`와 관련 아키텍처·도메인·보안 문서
- 실행한 자동 검증과 그 결과

기존 코드나 문서의 감사에서는 전체 diff 대신 지정된 검토 대상과 관련 계약을 확인한다.

작업 트리에 현재 요청과 관계없는 기존 변경이 있으면 이를 현재 작업의 변경과 구분한다.
관련 없는 변경을 수정하거나 되돌리지 않는다.

---

# 리뷰 지적 판단 기준

다음 중 하나에 해당하고 구체적인 영향과 재현 경로를 설명할 수 있을 때 리뷰 지적으로
보고한다. 변경 후 리뷰에서는 변경으로 인한 영향인지 확인하고, 기존 코드나 문서의
감사에서는 지정된 범위의 기존 문제도 포함한다.

- 요구한 동작을 만족하지 않거나 기존 동작을 잘못 변경한다.
- 애그리거트의 불변식이나 허용된 상태 전이를 위반한다.
- 아키텍처 의존 방향, 타입 소유권 또는 보안 경계를 위반한다.
- 실패·경계 조건에서 데이터나 상태가 잘못 처리된다.
- 테스트가 통과하더라도 실제 계약과 다른 결과를 만들 수 있다.
- 누락된 테스트 때문에 변경의 핵심 동작이나 회귀 위험이 검증되지 않는다.

다음 내용만으로는 리뷰 지적을 만들지 않는다.

- 프로젝트 기준으로 확정되지 않은 개인적인 스타일 선호
- 현재 요구사항과 무관한 미래 확장 가능성
- 실제 영향이나 발생 경로가 없는 추측
- 변경 후 리뷰에서 현재 변경과 관련 없는 기존 코드의 별도 문제
- 자동 포매터가 처리하는 형식 차이

현재 변경을 막지는 않지만 반복적으로 확인할 가치가 있는 관례는 `보완 제안`으로
분리한다. 보완 제안에는 관찰한 근거, 반복될 때의 위험과 기록하기 적절한 문서를 함께
제시한다. 프로젝트 공통 규칙은 `AGENTS.md`나 이 문서, 애그리거트 고유 정책은 해당
애그리거트 문서를 우선한다. 보완 제안을 새로운 규칙으로 임의 확정하거나 이를 근거로
요청 범위 밖의 코드를 자동으로 수정하지 않는다.

# 공통 리뷰 체크리스트

## 요구사항과 변경 범위

- 요청한 성공·실패 시나리오가 모두 구현되었는가?
- 변경이 요청한 수직 기능 범위에 집중되어 있는가?
- 관련 없는 리팩터링, 이름 변경이나 미래용 추상화가 포함되지 않았는가?
- 기존 공개 API와 저장된 의미를 의도하지 않게 변경하지 않았는가?

## 애그리거트와 도메인 모델

- 구현이 현재 도메인 문서의 “확정된 규칙”과 일치하는가?
- 상태 변경과 불변식 보호를 애그리거트가 소유하는가?
- 상태 전이가 애그리거트 불변식을 깨뜨리지 않는가?
- 상태에 따라 같은 필드가 서로 다른 의미를 갖게 되지 않았는가?
- 새로운 필드가 기존 필드와 중복된 사실을 저장하지 않는가?
- 계산 가능한 파생 값을 불필요하게 영속 상태로 만들지 않았는가?
- 상태 변경이 일반 setter가 아닌 의미 있는 도메인 행위로 표현되는가?
- 모든 생성·복원·상태 변경 경로에서 불변식이 유지되는가?
- 다른 애그리거트를 객체 그래프로 포함하지 않고 식별자로 참조하는가?
- 변경 가능한 컬렉션이나 내부 상태를 외부에 직접 노출하지 않는가?
- 생명주기 상태와 독립적인 원인이나 시간 개념을 하나의 상태로 합치지 않았는가?
- 값 객체와 도메인 예외가 실제 도메인 의미와 소유권에 맞는가?

구독, 상품, 청구, 결제 또는 배송 변경은 `docs/subscription.md`의 확정된 규칙과 후속 논의
대상을 다시 확인한다. 청구·결제 작업은 `docs/billing-payment.md`도 확인한다. 후속 논의
대상을 현재 구현 요구사항으로 취급하지 않는다.

## 날짜와 시간

- 날짜 범위의 시작과 종료 포함 여부가 명확한가?
- 실제 월의 마지막 날짜를 정확하게 사용했는가?
- 28일, 29일, 30일, 31일 경계를 검증했는가?
- 윤년과 월·연도 경계를 검증했는가?
- 같은 날과 다음 날 상태 전이를 각각 검증했는가?
- 반복 상태 전이에서도 값이 누적 오류 없이 유지되는가?
- 현재 시간 조회 책임이 애플리케이션의 KST `Clock`에 있고 도메인이 직접 조회하지
  않는가?

## 예외

예외를 HTTP 상태에 매핑하기 전에 “누가 이 문제를 해결할 수 있는가?”를 확인한다.

- 잘못된 클라이언트 입력이면 `400` 계열을 검토한다.
- 현재 리소스 상태와 요청의 충돌이면 `409` 계열을 검토한다.
- 정상 요청 흐름에서 발생해서는 안 되는 내부 불변식 위반, 잘못된 복원 또는
  프로그래밍 오류는 4xx로 노출하지 않고 5xx 계열 처리를 검토한다.

예외 타입이 실제 실패 원인을 표현하는지 확인한다. 클라이언트가 수정할 수 없는 문제를
`BAD_REQUEST`로 반환하지 않는다. 정상 실행 경로에서 도달할 수 없는 Exception Handler가
죽은 코드로 남아 있지 않은지도 확인한다.

## HTTP API

- 도메인, 유즈케이스, 포트, 테스트, 문서와 API가 같은 비즈니스 용어를 사용하는가?
- 동일 리소스를 API마다 다른 방식으로 식별하지 않는가?
- Controller signature 변경이 AOP, Security, Validation 같은 횡단 관심사에 영향을
  주지 않는가?

## 애플리케이션 서비스

- 애플리케이션 서비스가 유즈케이스 조율에 집중하는가?
- 도메인 객체가 소유할 규칙을 서비스에서 계산하거나 중복 검증하지 않는가?
- 필요한 애그리거트를 로드하고 도메인 행위를 호출한 뒤 올바르게 저장하는가?
- 명령과 조회의 책임이 섞이지 않았는가?
- 인증 주체와 외부 시스템 정보는 명시적인 포트를 통해 얻는가?
- 실패 시 일부 상태나 부수 효과만 반영되는 경로가 없는가?

## 포트와 어댑터

- 포트가 구현 기술이 아니라 애플리케이션이 필요로 하는 능력을 표현하는가?
- 어댑터의 프레임워크·HTTP·영속성 타입이 내부 계층으로 새어 나오지 않는가?
- 명령 포트와 조회 포트의 의미가 유지되는가?
- 요청·응답·영속성 매핑에서 값 누락이나 의미 변환 오류가 없는가?
- 외부 실패가 적절한 계층의 실패 의미로 변환되는가?

## 인증과 인가

- 인증된 주체에서 도메인 식별자를 얻고 클라이언트가 제출한 소유자 식별자를 신뢰하지
  않는가?
- 역할 기반 인가와 소유권 인가를 올바른 경계에서 수행하는가?
- Spring Security 타입이 도메인 또는 애플리케이션 규칙에 노출되지 않는가?
- 인가 실패와 리소스 부재의 의미가 의도한 API 계약을 따르는가?

구체적인 인증·인가 경계는 `docs/adr/security.md`를 따른다.

## Java 코드

- 필수 인자 null 검증에는 `Objects.requireNonNull()`을 우선 사용했는가?
- 도메인 불변식은 명시적인 조건문과 의미 있는 도메인 예외로 표현했는가?
- 일반적인 null 조건 비교는 `value == null`을 사용했는가?
- 검증 표현을 성능보다 의도와 책임을 기준으로 선택했는가?
- 객체와 컬렉션의 변경 가능성이 의도한 범위로 제한되는가?
- `equals`, `hashCode`와 값 객체의 동등성 의미가 일관되는가?
- 넓은 범위의 `catch`, 예외 무시 또는 원인을 잃는 예외 변환이 없는가?
- `null` 가능 값, enum 분기와 날짜 경계에서 빠진 경우가 없는가?
- 현재 시각이 필요하면 애플리케이션 계층의 KST `Clock` 계약을 따르는가?
- 이름과 메서드 구조가 비즈니스 의도와 하나의 책임을 드러내는가?

## 테스트

- 변경된 핵심 동작과 불변식을 가장 작은 적절한 범위에서 검증하는가?
- 정상 경로뿐 아니라 잘못된 상태 전이, 경계값과 실패 경로를 검증하는가?
- 도메인 테스트가 실제 애그리거트를 사용하는가?
- 애플리케이션 서비스 테스트가 실제 도메인 행위를 지나치게 mock 처리하지 않는가?
- 관찰 가능한 결과보다 내부 구현의 호출 횟수에 과도하게 결합하지 않는가?
- 여러 데이터를 조합하는 조회는 최종 조회 모델을 검증하는가?

세부 테스트 원칙은 `docs/testing.md`를 따른다.

## 문서와 용어

- 코드가 관련 문서의 확정된 규칙과 일치하는가?
- 새로 확정된 정책이나 중요한 결정 이유가 관련 문서에 반영되었는가?
- 공통 용어는 `docs/glossary.md`와 일치하는가?
- 아직 확정하지 않은 정책을 코드나 문서에서 확정된 것처럼 표현하지 않는가?
- 새로 확정된 정책이 후속 논의 대상에서 확정된 규칙으로 이동했는가?

# 자동 검증

Java 프로덕션 코드나 테스트를 변경했으면 완료 전에 다음 검증을 기본으로 실행한다.

```text
./gradlew spotlessCheck test
```

구현 중에는 관련 테스트를 먼저 실행할 수 있지만, 완료 전에는 변경의 영향을 포함하는 더
넓은 테스트 모음을 실행한다. 환경 문제나 권한 문제로 검증하지 못한 항목은 통과했다고
간주하지 않고 명령과 사유를 작업 결과에 기록한다.

최종 변경 상태에서 필수 검증이 통과했다면 새 변경, 실패 또는 미해결 우려 없이 검증을
확대하거나 반복하지 않는다.

문서만 변경한 작업은 Java 테스트를 생략할 수 있다. 대신 Markdown 형식, 내부 경로와
서로 참조하는 규칙의 일관성을 확인한다.

# 리뷰 결과와 반복

리뷰 결과는 다음 세 상태 중 하나로 정리한다.

- `PASS`: 작업 범위에 필요한 검증을 완료했고 수정할 리뷰 지적이 없다. 자동 검증이
  필요한 작업은 해당 검증이 성공해야 한다.
- `NEEDS_FIX`: 요청 범위 안에서 수정할 수 있는 리뷰 지적이 있다.
- `BLOCKED`: 확정된 규칙과 요구사항의 충돌, 환경 문제 또는 사용자 결정이 필요한 문제가
  있다.

각 리뷰 지적에는 다음 정보를 포함한다.

- 우선순위
- 파일과 위치
- 실제 문제가 발생하는 조건과 영향
- 위반한 프로젝트 규칙이나 코드 계약
- 요청 범위 안의 최소 수정 방향

수정이 요청 범위에 포함된 작업에서 `NEEDS_FIX`이면 근거가 확인된 항목만 최소 범위로
수정하고 필요한 검증과 리뷰를 다시 수행한다. 검토만 요청받은 작업에서는 수정하지 않고
리뷰 결과를 보고한다.

지적이 없으면 리뷰를 종료한다. 지적을 수정한 뒤의 재리뷰는 기본 최대 두 차례로
제한한다. 이는 필수 반복 횟수가 아닌 상한이다. 그 뒤에도 리뷰 지적이 남거나 같은
지적이 반복되면 임의로 범위를 넓히지 않고 남은 위험과 필요한 결정을 보고한다.
